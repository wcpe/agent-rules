# Git 提交规范（适用于所有仓库）

变更一律走 PR（豁免见 pr-workflow 规则），PR 标题 = 提交标题 = Release 笔记里显示的那行字。

## 1. 提交信息语言（强制）

- 标题（Description）和正文（Body）必须使用简体中文；type 与 scope 用英文小写。
- 格式：`<type>(<scope>): <中文描述>`，结尾不加句号。type 遵循 Conventional Commits（feat、fix、refactor、docs、chore、test、build、ci 等），scope 为英文小写模块名、可选。
- 正文用空行与标题分隔，中文撰写，可用 `-` 列要点；说明"为什么改"和"改动要点"，避免逐行复述 diff。
- 禁止任何形式的 AI 签名或尾注：`Claude`、`Codex`、`Generated by ...`、`Co-authored-by: ...` 等；消息末尾不附作者署名 / 工具署名 / 生成来源标记。

## 2. 禁止入库的内容（强制）

按内容性质判断，不按路径 / 文件名 / 扩展名判断。严禁入库：

- 计划文档：PLAN.md、plan-*.md、实施计划.md、roadmap.md 等。
- 临时 / 一次性需求文档：REQUIREMENTS.md、需求.md、requirement-*.md、临时 PRD 等（仓库规范化维护的 docs/PRD.md 除外）。
- 实施 / 执行 / 分析报告：IMPLEMENTATION.md、实施记录.md、执行报告.md、分析.md、重构报告.md、audit-*.md 等。
- AI 助手生成的过程性 Markdown 笔记（交流稿、思路记录、checklist 文档）。
- 全部当轮验收运行证据：原始日志、报告、trace、已填写或生成的 checklist、manifest、sidecar、实际读数、截图及其他图片 / 视频，包括截取、编码、改名、压缩或复制得到的版本；验收截图即使称为 golden 或基线也不能入库。

禁令适用于任何路径与载体：不得嵌入 PRD、规格、源码、注释或资源，不得搬目录、重命名、换扩展名、压缩归档绕过；过程材料仅存被忽略的 `.tmp/` 或库外；禁止 `git add -f` 绕过忽略规则。

### 2.1 允许入库的例外

- 长期维护的产品文档：README.md、CHANGELOG.md、docs/API.md 等；模块自身的对外 README。
- 配置 / 规则类：.claude/rules/*.md、AGENTS.md、CLAUDE.md。
- SDD 长期治理与规范文档：docs/PRD.md、docs/specs/**/*.md（不得夹带当轮运行结果）。
- 静态用例与断言预期、自动化测试 / 验收源码、确定性输入夹具；预期必须独立定义，不得把本轮实际读数改称「期望」。
- 产品图片、图标、纹理等产品资产（不是验收截图）。

### 2.2 误入库处理

- 提交前 `git status` 自查，误暂存则 `git reset HEAD <file>` 移除。
- 已误入库则单独提交一次 `chore: 移除误入库的过程性文档` 删除。
- 已跟踪文件不会因新增 .gitignore 自动清理，须在获授权的清理变更中显式移除。

### 2.3 隐私、机器路径与过程材料（强制）

- 提交文件、提交消息、PR 标题与正文、合并总结及 Git 作者 / 提交者身份：禁止密钥、令牌、密码、凭据、个人私有联系信息、真实机器用户名、内部地址等敏感内容；作者身份使用用户确认可公开的仓库身份。
- 禁止本机绝对路径：仓库内用相对路径，外置目录用环境变量或 `<仓库根>` 等占位符。
- 提交前审查 `git diff --cached` 完整差异及所有新增文件内容，并检查提交消息、作者身份与 PR 正文。
- 敏感内容已入库：追加删除只清当前版本，不宣称已从历史消除；确需清历史须先获用户明确授权，推送用 `--force-with-lease`；泄露凭据还须撤销或轮换。

## 3. 其他约束

- 一次提交只做一件事，不混入无关改动。
- 禁止跳过 hooks（--no-verify、--no-gpg-sign）。
- 禁止对已 push 的提交 --amend，应追加新提交。
- 提交前确认未包含 .env / 凭据 / 大型二进制等不应入库的文件。

## 4. 合并提交（squash）信息规范

合并一律 squash（见 pr-workflow 规则），合并提交五条硬规则：

1. 标题带 PR 编号 `<type>(<scope>): <中文描述> (#<n>)`——GitHub 不会自动附加，必须手写。
2. 正文总结 PR 全部实质提交（`gh pr view <n> --json commits --jq '.commits[].messageHeadline'` 逐条核对，可合并同主题，不得整条丢失）。
3. 正文禁止与 PR 描述雷同（两句以上即违规），以代码改动为主线压成更短叙述。
4. 一律纯文本，禁止 Markdown 标记 / 列表 / 复选框 / 表格 / 代码块 / 反引号。
5. 一律 `gh pr merge --squash --delete-branch`，禁用 --merge / --rebase。
