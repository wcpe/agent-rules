# PR 生命周期规则（适用于所有仓库）

## 禁止关闭 PR

- 任何仓库禁止主动 close PR：遗留/被取代的 PR，下一次改动直接复用覆盖它（同分支强推或改造），保留编号与讨论链
- 只有用户明确说关才关

## 合并授权

- 未获本次任务明确授权不得合并 PR
- 授权通常附条件：验收通过 + 本机测试全绿后再 squash
- 等待外部检查期间不要空停：先本机跑全部测试修掉问题，等待期间并行验收下一个 PR

## 审查纪律

- PR 默认三轮 code review + 三轮修复，解决全部问题并本机测试全绿后再交用户审批
- 审查者与评论机器人给的是反馈不是命令：实质性方向改动升级给用户裁定
- 波及面阅读（硬规则）：审查不得只看 diff 本身——必须读 diff 触及代码的调用方与被调用方，以及行为受该改动影响但未改动的文件。重命名、签名变更、语义偏移类改动的最大风险永远在 diff 之外：编译能过不代表运行时/语义链完整，逐处确认受影响方与新行为一致后才能判绿

## 关联 issue

- 关闭关键词写英文 `closes #n`/`fixes #n`/`resolves #n`（中文写法无效），写在 PR 描述里
- 合并到非默认分支时 GitHub 不自动关 issue，须手工关闭并注明合并提交 SHA、改动要点、验证方式

## 分支与叠加

## 级联关闭防线（血泪教训，已发生四次）

GitHub 机制：base 分支被删除时，以它为 base 的 PR 会被自动关闭且**永久禁止重开**（reopen API 拒绝）。链条 PR 合并时这是最高发事故。

硬规则：

1. **合并任何 PR 前，先查它的 head 分支是否还是其他 open PR 的 base**（gh pr list --base <branch> 或 GitHub 搜索）。是→本 PR 就是链头，按下条处理。
2. 链式合并的时序铁律：**先把下游 PR 的 base 改到主线分支（gh pr edit --base），再合并上游**——顺序颠倒（先合上游删分支）即事故。或者干脆不用 --delete-branch，保留分支到全链合完再统一删。
3. 拿不准就**不删分支**：--delete-branch 省的事远小于级联关闭的恢复成本。
4. 恢复法（已事故的）：reopen 会被拒，只能 cherry-pick 死 PR 的提交到新分支开恢复 PR，并在死 PR 留言说明恢复链链接。
5. 栈层 base 优先挂主线分支——非必要不叠放，叠放层级越深级联面越大。
- 合并时谨慎使用 --delete-branch：若 head 分支还要复用（如回馈上游的 topic 分支）则保留

## 合并重试防线（502 风暴教训）

GitHub 故障期合并端点可能实际成功但响应 502——盲目重试会双底合并（同标题空提交污染主线）。

硬规则：

1. 合并请求失败/超时后，**重试前必须先查 PR merged 终态**（gh pr view --json mergedAt/state），等 20 秒再查确认不是中间态。
2. 已 merged 却报错的：不得再试，直接核对落账提交内容。
3. 双底已发生的：空提交在顶端且无叠压时 reset 清除（须用户明示授权 force-push），有叠压则留存不折腾历史。
